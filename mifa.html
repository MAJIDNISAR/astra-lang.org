Mifa

Mifa is Astra's package manager, Cargo-shaped, agent-friendly, and built around one non-negotiable: the same inputs must always produce the same build.

Mifa, as a globe

Every Mifa feature is a star: the brightest work today, faint dotted ones are planned. Drag to turn it, or pick a magnitude.

  • Works today: mifa init, mifa add --path, mifa verify, mifa lock, Path dependencies, Package cache, mifa clean, --json on local commands, Registry protocol (34 tests), login + publish --dry-run
  • New in v0.10–v0.11: mifa build, mifa run, Importable dependencies, mifa test, Cargo-style manifests, build --release / --target
  • On main, next release: mifa --version, Honest mifa search
  • Next: Project-wide mifa verify, HTTP registry client, Staging registry, Real mifa publish
  • Planned: Hosted registry (mifa.dev), Global lockfile contract

From zero to running project

$ mkdir myapp && cd myapp
$ mifa init myapp          # scaffold astra.toml + src/main.astra here
$ mifa verify              # validate astra.toml and the src/ layout
$ mifa lock                # write astra.lock (sha256-stable)
$ mifa run                 # compile + execute natively
$ mifa verify --json       # same result as a machine-readable envelope
$ mifa login <token>       # store a registry token (~/.mifa/credentials.toml)
$ mifa publish --dry-run   # validate + archive + checksum, no upload
$ mifa clean --cache       # drop target/ and ~/.mifa/cache

The manifest is plain TOML. This is exactly what mifa init writes; today every field shown is required:

astra.toml 
name = "myapp"
version = "0.1.0"
description = "A new Astra package"
authors = []
keywords = []
categories = []

[dependencies]

[build_dependencies]

[target_dependencies]

Add dependencies with mifa add rather than by hand: the entry it writes is verbose today. A Cargo-style [package] section and a short lib = { path = "../lib" } form are planned.

The lockfile

mifa lock resolves the full dependency graph and writes astra.lock: versioned, sorted, and content-hashed. Two machines with the same manifest resolve identical graphs, byte for byte. This was validated as differentiator D5: repeated locks of the same workspace produce sha256-identical files.

Reproducibility matters twice over for Astra's mission. Humans get reliable CI; agents get a guarantee that a build that verified once will verify the same way again, no drifting dependencies invalidating an earlier repair loop.

Honest note: the registry protocol is fully specified and tested against an in-memory implementation, checksums, yanked versions, auth, and publish validation all work, but there is no hosted registry yet; real uploads are blocked on deployment, and a registry dependency like utils@1.0.0 has nothing to download from. Local workflows (init, verify, lock, run, path dependencies, JSON output, login, dry-run publish) are real and covered by 90+ tests.

Dependencies you can import

A local package is a real dependency. mifa build compiles src/main.astra to target/<name> and searches each path dependency's src/ folder for modules; mifa run passes arguments through and exits with your program's exit code.

$ mifa init app              # creates app/
$ mifa init textutil
$ cd app
$ mifa add textutil --path ../textutil   # checks ../textutil/astra.toml
$ mifa run
HI!
textutil/src/textutil.astra · app/src/main.astra 
pub fn shout(s: str) -> str:
    return s.to_upper() + "!"

import textutil
fn main() -> int:
    print(textutil::shout("hi"))
    return 0

mifa add without --path is an error instead of recording a package nothing can fetch. This flow is covered by an end-to-end test that drives the real mifa binary.

Honest about the registry next release

On main, not in a release yet:

  • mifa --version prints the Mifa version.
  • mifa search says the registry is not deployed instead of listing packages. In v0.11.2-alpha, mifa search lists packages that do not exist; that is a known bug in that release.
  • The Mifa flow is part of the black-box release suite that runs on every platform before a release publishes.

Why not reuse an existing manager?

  • Verification-first. astra verify type-checks a program without generating code, so an agent can validate a change in milliseconds. mifa verify today checks only the manifest and layout; type-checking the whole project graph from Mifa is planned.
  • Lockfile as a contract. The lock isn't advisory; future registry fetches will refuse checksum mismatches outright.
  • One tool, one mental model. Mifa wraps the same compiler library the astra CLI uses. Diagnostics, exit codes, and JSON shapes stay identical between both tools, init, add, verify, test, lock, login and publish support --json and emit the same diagnostics[] envelope.
